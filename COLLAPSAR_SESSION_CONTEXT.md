## 1. Что это за проект

COLLAPSAR Report System — бэкенд + фронтенд для командной структуры Star Wars
Garry's Mod сообщества, завязанной на Discord. Бот живёт на **одном**
Discord-сервере (гильдии); формирования (регименты — 501st, Гвардия и т.д.)
различаются по Discord-ролям внутри этого одного сервера, не по отдельным
серверам. Авторизация — Discord OAuth2 + членство по ролям гильдии; сессии —
JWT (без cookies).

**Деплой**:self-hosted (Debian/Proxmox VPS) через `docker-compose.yml` +
Cloudflare Tunnel, same-origin (FastAPI отдаёт собранный фронтенд из
`frontend/dist`, монтируется последним, чтобы не перекрывать `/api`, `/auth`,
`/health`, `/uploads`). Self-hosted GitHub Actions runner на VPS **автоматически
деплоит на каждый push в `master`** — пуш в master сразу уходит в прод, staging
нет. Контейнер на каждом старте гоняет `alembic upgrade head`, поэтому схемные
миграции применяются автоматически при деплое; **бэкфиллы данных для новых фич —
нет**, это отдельный ручной шаг через `docker exec` после деплоя.

**Стек**: FastAPI (Python) + React/Vite. Нет автотестов вообще (ни бэкенд, ни
фронтенд) — верификация изменений всегда идёт вручную (curl + локальная БД,
`npm run build`).

**Docker-контейнеры на проде** (имена из `docker-compose.yml`):
- `collapsar-postgres` — Postgres
- `collapsar-backend` — FastAPI
- `collapsar-tunnel` — Cloudflare Tunnel

## 2. Архитектура (актуальное состояние CLAUDE.md)

### Слоение бэкенда
Каждая фича — четыре файла с одинаковым именем: `app/models/x.py` (SQLAlchemy),
`app/crud/x.py` (async DB-функции, без HTTP), `app/schemas/x.py` (Pydantic
read/create/update), `app/api/x.py` (FastAPI роутер, права, склеивает
crud+schemas). `app/main.py` регистрирует каждый роутер под `/api`, кроме auth.
**Новые модели обязательно импортировать в `app/models/__init__.py`** —
SQLAlchemy резолвит строковые ссылки на relationship через этот общий реестр
при конфигурации мапперов; модель, забытая в `__init__.py`, ломает связи других
моделей непонятным образом (был реальный баг с `Character` — забыли, поймали
на аудите).

`app/api/events.py` (SSE-канал живых обновлений, `/api/events`) и
`app/api/event_room.py` (фича "Ивентрум", `/api/event-room/*`) — не связаны
между собой, несмотря на похожее имя.

### Переиспользуемые хелперы (не изобретать заново)
- `app/core/uploads.py::read_image_upload(file, allowed_types, max_size)` —
  единственный правильный способ принять загруженную картинку: читает
  ограниченными чанками (никогда не буферизует больше max_size до отказа) и
  проверяет, что байты реально декодируются как изображение (Pillow), а не
  просто доверяет `Content-Type` от клиента. Используется для картинок
  рапортов, фото участников, картинок карт ивентрума.
- `PATCH`/`DELETE` crud-функция, чья строка может легитимно быть referenced
  другими строками (FK без `ondelete`) — ловить `IntegrityError`, `rollback()`,
  поднимать дружелюбный `AppError` (см. `report_category_crud.delete`,
  `squad_crud.delete`). **Снимать нужное для сообщения поле в локальную
  переменную ДО commit, который может упасть** — после `rollback()` атрибуты
  ORM-объекта просрочены, обращение к ним внутри `except`-блока роняет
  `MissingGreenlet` (ленивая подгрузка не может awaitить в этом контексте).
- Инвариант "не больше одной pending X на Y" — partial unique index
  (`CREATE UNIQUE INDEX ... WHERE status = 'pending'`), не просто
  app-level check-then-insert (см. `PromotionRequest.__table_args__` /
  миграция `0075`). Пара с `IntegrityError`-catch на инсерте.

### Permission model — `AccessContext` (`app/api/deps.py`)
Каждый эндпоинт зависит от `get_access_context`, которая считает один
`AccessContext` dataclass на запрос в `_compute_permission_fields()` из живых
Discord-ролей пользователя + состояния БД (`RegimentCommander`, ролевые
настройки `AppSettings` и т.д.). Единственный источник правды "может ли этот
пользователь X" — проверять здесь, не городить ad-hoc права в эндпоинте.
Ключевые поля: `is_admin`/`is_high_command` (глобальные), `commander_regiment_ids`
(явное назначение через `RegimentCommander` — role_type
commander/deputy/mentor, **не** просто наличие Discord-роли формирования),
`category_manager_regiment_ids` (подмножество, где role_type именно
`commander`, гейтит настройку баллов рапорта), `soldier_regiment_ids`, методы
`is_commander_of(regiment_id)` / `can_appeal_report(regiment_id)`.

`GET /api/me` сериализует `AccessContext` в plain JSON (`app/schemas/me.py`),
который берёт фронтендовый `AuthContext`. До фронта доходят только явно
перечисленные в этой схеме поля.

"View as" (`X-View-As-Role`/`X-View-As-Discord-Id`, только admin/high-command)
даёт стаффу смотреть приложение глазами другой роли/человека —
`build_view_as_context` строит урезанный `AccessContext` для этого пути; при
добавлении нового permission-поля проверять, нужно ли его туда тоже прокинуть
(этой сессией **не** прокинули `recruit_regiment_id` туда — осознанное решение,
см. раздел 4).

### Report system (крупнейшая подсистема)
- `ReportCategory` — категория рапорта на формирование, JSON-поле `fields`
  (`{name, type: "text"|"roster", allowed_regiment_ids, default_self,
  allow_manual}`). `points`/`participant_points` авто-начисляются при
  одобрении. Системные булевы флаги: `is_detention` / `is_promotion` /
  `is_demotion` / `is_training` / **`is_recruit_promotion` (новый, эта
  сессия)** — взаимоисключающие друг с другом и с `is_joint`.
  `open_to_regiment_leadership` открывает подачу командирам/замам ДРУГИХ
  формирований — `is_recruit_promotion` идёт дальше: обходит членство в
  формировании вообще (см. раздел 4).
- Два независимых кросс-формационных механизма, легко перепутать:
  `mirrors_to_category_id` (1:1, статичный read-only дубль) vs `is_joint`
  (1:many, независимое решение каждого формирования-участника, таблица
  `ReportRegimentDecision`).
- Членство в формировании по Discord id **не хранится** — резолвится живым
  запросом `discord_client.fetch_guild_members()` + сверкой
  `regiment.discord_role_id`.

### SQLAlchemy async gotcha (регулярный источник багов)
`db.get(Model, id)` возвращает объект из identity map сессии, если он уже там
загружен, **молча игнорируя** переданный `options=[selectinload(...)]`. Каждая
`get_by_id`-функция в проекте передаёт `populate_existing=True`.

### Discord-интеграция (`app/core/discord_client.py`)
REST через `httpx`, без `discord.py`, без gateway, без постоянного
bot-процесса. Почти всё — GET (read-only); **`add_member_role` (эта сессия) —
единственное исключение**, bot-token `PUT`, может вернуть 403, если у бота нет
`MANAGE_ROLES` или его роль ниже целевой в иерархии сервера — вызывающий код
обязан относиться к этому как best-effort (залогировать и продолжить, никогда
не ронять запрос).

### Frontend-конвенции
- Каждый async-обработчик кнопки/формы обязан оборачивать `api.*`-вызов в
  try/catch и показывать ошибку — `showToast(e.message, "error")` для
  разовых действий, локальный `error` state для форм. Применено повсеместно
  после аудита этой сессии (см. раздел 3).
- Любой `useEffect`, который грузит данные по быстро сменяемому значению
  (регимент/участник/фильтр), нуждается в request-generation guard
  (`requestIdRef`), иначе устаревший ответ может перезаписать более свежее
  состояние. Тоже применено повсеместно.
- Пользовательский URL, рендерящийся как `<a href>` — через `utils/safeUrl.js`
  (только http/https).
- `hooks/useTheme.js` — `useTheme()` (тумблер, один раз в Navbar) +
  `useThemeValue()` (read-only, реактивно для графиков).

### React Router / фронтенд
`HashRouter` (`#/...`), `?code=` от Discord OAuth парсится в начале
`AuthContext` до роутера. Собирается в `frontend/dist`, отдаётся same-origin.

### 3.1 Текущий диалог — быстрые точечные фиксы

**Steam ID не рендерился ссылкой.** Скриншот показал, что у одного бойца
STEAM:ID был обычным текстом (SteamID64, 17 цифр), у другого — рабочей ссылкой
(`STEAM_0:0:...`). Причина: `steamProfileUrl()` во фронтенде понимал только
формат `STEAM_X:Y:Z`, хотя бэкенд (`app/schemas/validators.py::validate_steam_id`)
уже давно принимает и нормализует оба формата на запись. Скорее всего, старые
записи в БД остались в сыром SteamID64-формате ещё до появления нормализации.
**Решение**: `frontend/src/utils/steam.js` теперь распознаёт оба формата
(regex на 17 цифр в дополнение к `STEAM_[0-5]:...`), без миграции БД — защитный
фикс на отображении, а не гонка за легаси-данными.

**"После разморозки не поднимается снова вверх".** Скриншот страницы
"Формирования" — активные сверху, замороженные снизу, но после разморозки
формирование не возвращалось наверх списка. Причина: `regiment_crud.get_all()`
не имел `ORDER BY` вообще — Postgres отдавал строки в физическом порядке
хранения, а UPDATE (заморозка/разморозка — тоже UPDATE) переставляет
физическую версию строки, из-за чего порядок в выдаче плавал сам по себе.
**Решение**: добавлен `.order_by(Regiment.is_archived, Regiment.id)` —
активные сверху детерминированно, id — стабильный порядок внутри группы.

### 3.2 Обсуждение: рекрутская система

**Исходный запрос пользователя** (дословная суть): при регистрации человек
автоматически получает звание рекрута и находится "под 17-м Передовым
Полком". Обучать рекрутов может любой Капрал+ (CPL+). После регистрации на
сайте на бойца пишут рапорт об обучении, он становится PVT 17-го полка, а
дальше может переводиться в другие формирования как обычно. Повышать его
может любой admin+ и/или зам командира ЛЮБОГО формирования, но он не должен
"светиться" как их боец — найти можно только по нику в отдельной "Рекрутской".

Я предложил идеи по каждой развилке (с trade-off'ами), пользователь выбрал:

| # | Развилка | Выбор |
|---|---|---|
| 1 | Как новичок физически попадает в 17-й полк | **B** — сайт сам вешает Discord-роль при регистрации |
| 2 | Рапорт об обучении → сразу PVT | **A** — отдельная системная категория, прямая смена rank_id при одобрении |
| 3 | Кто может повышать рекрутов | **A** — точечное исключение в проверке доступа (любой командир/зам ЛЮБОГО формирования) |
| 4 | Как найти рекрута по нику | **A**, плюс "или вообще завести Рекрутскую" → решили строить отдельную страницу |

Плюс отдельно всплыл баг со Steam ID (см. 3.1).

### 3.3 Обсуждение: ступень "Старший" в дисциплинах (MED/ENG/PIL)

Пользователь показал орг-схему медицинского корпуса:
`Стажёр → Специалист (1 из 3 веток: Вирусология/Дефектология/Хирургия) →
Старший медик (все 3 ветки разом) → [Глава ветки ИЛИ Инструктор, параллельные
пути] → DEP → CO`.

Вопрос: как это реализовывать, учитывая, что у инженеров и пилотов свои такие
же ветки — "лучше показать один MED для всех глаз, а внутри отдела настраивать
повышения"?

**Мой ответ**: подтвердил, что идея "один MED снаружи" уже почти то, как
устроена система (категория `medic`/`pilot`/`engineer` уже кросс-формационная,
не привязана к `Regiment`). 4 из 6 ступеней лестницы уже покрыты существующими
механизмами (`parent_id` для Специалиста, `InstructorRole.tier` для
Инструктор/Зам/Куратор).两 реальных пробела:

- **"Старший" (все 3 ветки разом)** — `parent_id` умеет только "нужен один
  конкретный родитель". Варианты: (A) чисто вычисляемый бейдж без сущности,
  (B) реальная 4-я специализация с проверкой "уже есть все 3 дочерних".
  **Пользователь выбрал B.**
- **"Глава ветки"** — изначально предложил как "то же самое, что инструктор".
  **Пользователь поправил**: это НЕ роль в программном смысле, это чисто
  РП-титул — даёт право командовать по РП теми, кто ниже, но **не даёт права
  обучать никого**, и при этом не запрещает самому главе обучаться на другие
  ветки (это отдельно, через обычный инструкторский путь). **Итог: ноль
  изменений в коде** — чистый Discord-титул за выслугу, программно система про
  него ничего не знает.

## 5. Ключевые решения и их обоснование (trade-offs)

1. **Выдача Discord-роли — best-effort, никогда не блокирует регистрацию.**
   Права бота (`MANAGE_ROLES`) и его позиция в иерархии ролей — конфигурация
   Discord-сервера вне контроля приложения; жёсткая ошибка тут была бы хуже,
   чем тихий лог + продолжение.

2. **Право повышать рекрутов расширено по `regiment_id == recruit_regiment_id`,
   а не по коду звания (`RCT`).** Изначально в обсуждении фигурировал вариант
   "если у цели звание RCT" — но это покрывало бы только момент RCT→PVT, а
   реальная потребность пользователя ("повышать его может любой admin+/зам")
   касается ВСЕГО времени, пока боец числится в 17-м полку (в том числе уже
   после PVT, до перевода в другое формирование). Регимент-based условие
   решает это чище и не требует протаскивать код звания через сигнатуру
   `can_decide_promotion`.

3. **"Рекрутская" — отдельная read-only страница, не расширение
   `RosterBrowserModal`.** Рассматривался вариант просто разрешить всем
   командирам открывать полный состав 17-го полка через существующий
   ростер-браузер — отклонён, т.к. это дало бы заодно доступ к вещам, которые
   не просили (полная выслуга, дисциплина и т.д. чужого формирования).
   Узкий, специально написанный эндпоинт/страница держит границу чище.

4. **"Курс молодого бойца" полностью обходит проверку членства в
   формировании**, а не просто открывается командирам/замам через
   `open_to_regiment_leadership` (как категории Штаба). Причина: пользователь
   явно сказал "любой Капрал+", а не "любой командир/зам" — это принципиально
   шире существующего механизма, понадобилось отдельное условие-обход в
   `create_report`.

5. **Ступень "Старший" — отдельная таблица `SpecializationPrerequisite`, не
   переиспользование `parent_id`.** Пользователь сам выбрал этот вариант
   (B) вместо чистого вычисляемого бейджа — потому что хочет реальную
   сущность в каталоге специализаций, выдаваемую как обычно (через
   рапорт/прямую выдачу инструктором), а не просто UI-индикатор.

6. **"Глава ветки" — вообще без кода.** Ключевое уточнение пользователя:
   право чисто ролевое/РП ("командовать по РП"), не про обучение, не
   ограничивает обучение самого главы на другие ветки. Единственный
   правильный вариант — не трогать backend/permission-модель вовсе.

7. **CLAUDE.md обновляется после каждого крупного блока изменений** —
   явное требование пользователя из более ранней части сессии ("не забудь все
   изменения вносить себе в файлик"), соблюдалось по всей текущей сессии тоже.

## 6. Проблемы, которые решали, и их причины/решения

| Проблема | Причина | Решение |
|---|---|---|
| Steam ID не рендерится ссылкой у части бойцов | Легаси-записи в сыром SteamID64-формате, фронтендовый парсер понимал только STEAM_X:Y:Z | `steam.js` теперь распознаёт оба формата |
| Список формирований не поднимает обратно наверх после разморозки | Нет `ORDER BY` — Postgres отдаёт физический порядок хранения, который UPDATE (заморозка/разморозка) меняет сам по себе | Добавлен `order_by(is_archived, id)` |
| Рекрутам негде централизованно "приземляться" при регистрации | Не было механизма авто-назначения формирования/роли | 17-й полк как единая точка входа + `add_member_role` |
| Обучение рекрута требовало отдельного решения командира | Обычные рапорты не мутируют звание напрямую | Новый системный флаг `is_recruit_promotion` с прямой мутацией `rank_id` на авто-одобрении (по шаблону `is_training`) |
| Право повышать рекрутов было заперто на командиров именно 17-го полка | `can_decide_promotion` жёстко привязан к `commander_regiment_ids` целевого формирования | Точечное исключение по `recruit_regiment_id` |
| Заявка на повышение рекрута была видна по праву, но не в списке | `list_promotion_requests` фильтрует вручную, не через `can_decide_promotion` | Расширили набор `regiment_ids` тем же способом |
| Нельзя было найти рекрута, не будучи членом/командиром 17-го полка | `get_members` требовал членства/командования конкретно этим формированием | Узкое исключение в `get_members` + отдельная страница "Рекрутская" |
| Специализация "Старший" (все 3 ветки разом) нечем было выразить | `parent_id` — только "один конкретный родитель" | Новая таблица `SpecializationPrerequisite`, отдельная проверка в `_check_can_grant` |
| При тестировании: многостейтментные `psql -c "...; ...; ..."` откатывались целиком при ошибке в последнем стейтменте | psql выполняет несколько `;`-разделённых команд в одном `-c` как единую неявную транзакцию | Разбили на отдельные `psql -c` вызовы по одному стейтменту |
| `MissingGreenlet` при удалении категории с рапортами (более ранняя часть сессии) | Обращение к атрибуту ORM-объекта внутри `except` после `rollback()` — объект просрочен | Снимок нужного поля в переменную ДО commit |

## 7. Конфигурация и окружение

### Локальная разработка (Windows)
- Backend venv: `./.venv/Scripts/python.exe` (не системный `python` — тот
  триггерит заглушку Microsoft Store на этой машине).
- Запуск dev-бэкенда: `./.venv/Scripts/python.exe -m uvicorn app.main:app
  --port 8000`.
- Локальный Postgres — **plain `docker run` контейнер** `collapsar-postgres`
  (НЕ часть прод `docker-compose.yml`, у которого нет host-порта наружу для
  БД). Порт `5433`. Если контейнера нет — создать и восстановить из
  `backups/*.sql`, затем `alembic upgrade head`.
  ```
  docker run -d --name collapsar-postgres -e POSTGRES_USER=postgres \
    -e POSTGRES_PASSWORD=Kolobok2004 -e POSTGRES_DB=collapsar \
    -p 5433:5432 postgres:17-alpine
  ```
- Миграции: `alembic/versions/NNNN_description.py` вручную по номеру (не
  `--autogenerate`). Схема отдельно от бэкфиллов (бэкфиллы — одноразовые
  скрипты через `docker exec` после деплоя).
- Frontend: `npm install`, `npm run dev` (Vite), `npm run build` →
  `frontend/dist`.
- `curl` с кириллицей инлайн в Git Bash (`-d '{"name":"Пост"}'`) ломает
  кодировку — писать тело в файл, `--data-binary "@file"`.
- Фоновые `uvicorn`/`vite` процессы без `--reload` не подхватывают изменения
  файлов сами — проверять `Get-CimInstance Win32_Process` на зависшие
  процессы.
